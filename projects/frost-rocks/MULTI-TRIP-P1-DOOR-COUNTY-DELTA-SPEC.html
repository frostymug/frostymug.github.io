Multi-Trip P1 — Door County Delta Spec

Izzy (Design) | 2026-07-26 | Status: DESIGN-LOCKED, feasibility pass needed (Arya) before build. Target ship: before Door County departure (~Aug 2, ~1 week). Design target context: MULTI-TRIP-AND-PLACES-TARGET-MODEL.md. Prototype: published-html/multi-trip-v0-explore/ (P1 is the chosen direction; landing page has pros/cons of all four). Repo verified: aspen-frost/frost-rocks — src/db/schema.ts (migrations at v6), src/db/trips.ts, src/types/index.ts, app/index.tsx, app/map.tsx, src/components/BottomNav.tsx.

---

0. Scope in one paragraph

Turn Frost Rocks from a single-hard-coded-trip app into a multi-trip app for the Door County trip, using the P1 navigation model (trip name in the notebook header → quiet dropdown shelf) plus a minimal Trips management tab (create trip / mark previous / set current) that replaces the hard-coded trip. Capture stays present-tense to the current trip; the timeline scrolls across all trips; the map stays scoped to the current trip using the existing static-image approach, now selected per trip. No Places, no capture-without-a-trip, no MapLibre, no T1/T3 — those are the target model (§7 of the target note), not this build.

This spec separates STRUCTURE (IA, data, state — the load-bearing changes) from SKIN (visual dressing) — the v2.1 lesson: don't bury a structural delta inside "skin."

---

1. What exists today (verified, so the delta is honest)

  • Single trip, hard-coded. getOrCreateDefaultTrip() (src/db/trips.ts) returns the first/only trip; DEFAULT_TRIP_TITLE = 'Finland 2026'. Called in app/_layout.tsx, app/index.tsx, app/map.tsx. There is no notion of a current trip beyond "the one row that exists."
  • trips table (schema.ts, migration v1): id, title, start_date, end_date, created_at. renameTrip() exists; no create-additional / set-current / end.
  • encounters.trip_id is NOT NULL REFERENCES trips(id); index idx_encounters_trip(trip_id, captured_at DESC). listEncounters(tripId), countReviewQueue(tripId), etc. all already take a tripId — the data layer is already multi-trip-ready.
  • Nav: BottomNav (Notebook · Map · [+Capture] · Review) is rendered per-surface (not expo-router Tabs), with a reserved empty 5th slot and a code comment: "4 real slots > 1 fake one — Trip slot deferred until the surface exists." That surface now exists.
  • Map: app/map.tsx + src/components/FinlandMap.tsx — a static raster PNG (finland-map.png) with a fixed projection (FINLAND_MAP_WIDTH/HEIGHT, mapProjection.ts) and a Finland-only bounds check. This is the one piece hard-wired to a place.
  • Migrations are versioned (MIGRATIONS[], currently through version: 6), additive, run in order.
  • Events via logEvent(type, data); EventType is a closed union in types/index.ts.

---

2. STRUCTURE — the load-bearing changes

2.1 A single source of truth for "the current trip" (D-CUR)

The most important structural change, and the discipline that keeps the target model reachable. Introduce one accessor for the current context so no surface re-implements "which trip":

- getCurrentTrip(): Promise<Trip> — replaces getOrCreateDefaultTrip() at call sites. Returns the trip flagged current; if none, falls back to most-recently-created (never returns null in Door County scope). - setCurrentTrip(tripId) — sets the current pointer. - listTrips(): Promise<Trip[]> — for the shelf + Trips tab, newest-first. - createTrip({title, start_date?, end_date?}): Promise<Trip> — and makes it current. - markTripPrevious(tripId) / trip state (see 2.2).

  • New concept: current trip id, persisted (e.g., a app_state row or a single-row settings table, or a current flag on trips — Arya's call, §4).
  • New helpers in src/db/trips.ts (names indicative):
  • Discipline (from target note §6): every surface reads the current trip from getCurrentTrip(). Do not propagate getOrCreateDefaultTrip() into new code. getOrCreateDefaultTrip() may remain only as the first-run seeding of trip #0.

2.2 Trip state (D-STATE)

Add a state to trips: previous | active | upcoming. Minimum viable:

  • Store as a column on trips (state TEXT NOT NULL DEFAULT 'active') OR derive active from the current-trip pointer + dates. Design preference: an explicit state column, because the target model hangs T1/T3 behavior off it and because "current" (one trip) and "active" (a state) should not be permanently fused. Arya to confirm cheapest correct option (§4, D3-Q-style).
  • v1 behavior: exactly one trip is active/current at a time; marking a new trip current sets the old one previous. upcoming is settable in the Trips tab but drives nothing yet (inert label, per target §5).

2.3 Migration (D-MIG) — additive, version 7 (+ maybe 8)

  • ALTER TABLE trips ADD COLUMN state TEXT NOT NULL DEFAULT 'active'; (if going with explicit state).
  • Current-trip persistence: either ALTER TABLE trips ADD COLUMN is_current INTEGER NOT NULL DEFAULT 0 (+ backfill the sole existing Finland row to is_current = 1), or a tiny app_state(key, value) table. Arya picks; backfill must make the existing Finland trip current and active so nothing breaks for the live user.
  • No change to encounters (trip_id stays NOT NULL — Door County always has a trip). Do not weaken trip_id in this build.

2.4 Notebook header shelf (D-SHELF) — the P1 navigation

On app/index.tsx:

  • Header shows the current trip title as a tappable control + a state chip, with the existing quiet context sub-line beneath (place · N encounters · N today).
  • Tapping reveals a dropdown shelf listing listTrips() newest-first, each row: state dot, title, place/dates/count, state chip, check on current. Selecting a trip calls setCurrentTrip() and reloads the notebook to that trip.
  • Guardrail: the current trip title is always visible in the header — this is the capture guardrail (you always see which trip you're capturing into). The shelf is a review/browse gesture; selecting a trip is deliberate.
  • Prototype reference: p1.html (shelf open state screenshotted in the review package).

2.5 Trips management tab (D-TRIPS) — fills the reserved slot

Andy chose to stand this up now (option b), not retrofit later.

- List all trips grouped by state (Active / Upcoming / Previous). - Create trip (title required; dates optional) → becomes current + active. - Mark current trip as previous ("End this trip") and/or Set current on another trip. - (Rename already exists via renameTrip.)

  • BottomNav: fill the reserved 5th slot with Trips (NavSlot gains 'trips'; add onTrips). New route app/trips.tsx.
  • Minimum viable management (this is the whole point — it kills hard-coding):
  • Built as Trips but structured so "& Places" is additive later (don't hard-assume every row is a trip in the list-rendering seam). Reference: p3.html grouping; but note this tab is management, not the daily roam gesture (that's the header shelf).
  • Out of scope: ending-a-trip ceremony, T1 prep, itinerary editing, Places.

2.6 Timeline = all trips; Map + capture = current trip (D-SCOPE)

  • Notebook timeline: show the current trip's encounters up top, and allow scrolling back into previous trips' encounters grouped under a trip rule/divider (prototype universalTimeline). This satisfies Andy's C2 ("see all previous encounters from all trips by scrolling"). Design note: keep the current trip's encounters as the default/top view; the cross-trip scroll-back is additive below, not a mixed firehose.
  • Map: scoped to the current trip only (unchanged behavior, now per-trip).
  • Capture: writes trip_id = getCurrentTrip().id. Unchanged flow; just sources the trip from the new accessor.

2.7 Map generalized off "Finland" (D-MAP) — the floor, done carefully

This is the trickiest structural bit because the map is hard-wired to Finland.

  • Floor approach (locked): each trip can have a static field-map image + projection bounds, selected by current trip. Door County gets its own image + bounds; Finland keeps its existing one.
  • Introduce a map descriptor per trip (image asset + projection bounds + label). For v1 this can be a small static config keyed by trip (not necessarily a DB column) — e.g., a tripMaps registry mapping trip id/slug → { image, bounds, label }, with a graceful "no map for this trip" empty state.
  • Refactor FinlandMap/mapProjection so the image + bounds are inputs, not constants (rename to a generic FieldMap with a descriptor prop; keep Finland as one descriptor). This is the MapLibre seam — later, a descriptor can be "interactive tiles" instead of "static image" without touching callers.
  • Asset need (blocking, non-eng): a Door County static map image + its geographic bounds. Izzy to produce/source the Door County map asset + bounds (see §6 open items). Cassian/Arya to confirm asset pipeline (where map images live: assets/map/).

2.8 Events (D-EVT)

Add to EventType: trip_switch (from shelf), trip_create, trip_set_current, trip_mark_previous, trips_tab_open. Instrument the shelf + Trips tab so we can see whether Andy actually roams. Keep payloads minimal ({trip_id}).

---

3. SKIN — visual dressing (no logic)

Separated deliberately so it can be a distinct PR and doesn't hide structure.

  • Header trip-title control styling + state chips (previous/active/upcoming) per the field-guide tokens (src/theme/tokens.ts) — colors already prototyped in app.css.
  • Dropdown shelf sheet styling (scrim, rounded drop, trip rows) — prototype p1.html.
  • Trips tab cover/card styling — prototype p3.html (cover art can be a simple tinted block per trip in v1; no real photography needed).
  • Timeline trip-divider rule styling (prototype .triprule).
  • Empty states: "no map for this trip," "upcoming trip — no encounters yet."

4. Feasibility questions for Arya (answer before build)

  • MT-Q1 (current-trip persistence): is_current column on trips vs. a tiny app_state(key,value) table vs. deriving from state+dates? (Design wants an explicit, unambiguous current pointer + explicit state; pick the cheapest correct one.)
  • MT-Q2 (state storage): explicit state column vs. derived? (Design leans explicit — target model hangs behavior off it.)
  • MT-Q3 (map descriptor): static per-trip config registry vs. DB columns for map asset/bounds? For v1 a code-side registry seems cheapest; confirm it doesn't fight the asset pipeline.
  • MT-Q4 (migration plan): confirm v7 (+v8) additive migrations + the backfill that makes the existing Finland trip is_current=1, state='active'. Any risk to the live TestFlight user's data?
  • MT-Q5 (PR sequence): proposed below — confirm/resequence.

5. Suggested PR sequence (gate discipline; test each seam)

  • PR-MT1 (STRUCTURE, data): migration v7/v8 + trips.ts accessors (getCurrentTrip/setCurrentTrip/listTrips/createTrip/state) + backfill. Swap getOrCreateDefaultTrip() call sites to getCurrentTrip(). Gate: existing single-trip behavior identical for the live Finland data.
  • PR-MT2 (STRUCTURE, map seam): refactor FinlandMap→FieldMap(descriptor) + mapProjection to take bounds as input; Finland as one descriptor; add Door County descriptor + asset. Gate: Finland map renders exactly as before.
  • PR-MT3 (STRUCTURE, nav): header shelf on app/index.tsx + BottomNav 5th slot + app/trips.tsx management tab (create/set-current/mark-previous). Gate: create a 2nd trip, switch, capture lands in the right trip.
  • PR-MT4 (STRUCTURE, timeline): cross-trip scroll-back on the notebook timeline. Gate: previous-trip encounters appear below current, grouped, without breaking the by-event grouping seam.
  • PR-MT5 (SKIN): the §3 visual pass + events (§2.8).

6. Acceptance (does it earn Door County?)

  • A1. Andy can create "Door County," it becomes current, and capture lands in it — with Finland preserved and switchable. (The MVP, Andy's C2.)
  • A2. The current trip is unmistakable on the capture path (header always shows it); switching is deliberate, never incidental. (The guardrail — FR-MT-02.)
  • A3. Timeline scrolls back into Finland encounters from the Door County notebook. (C2.)
  • A4. Door County shows its own static field map; Finland's map is unchanged. (Floor map.)
  • A5. The capture-export-WoZ sequence works exactly as it did in Finland. (Andy C3 — sacred.)
  • A6. No getOrCreateDefaultTrip() assumptions leak into new code; map image+bounds are inputs. (Target reachability — future-proofing, not user-visible.)
