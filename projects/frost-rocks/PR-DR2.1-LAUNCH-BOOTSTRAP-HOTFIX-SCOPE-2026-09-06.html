Frost Rocks — PR-DR2.1 Launch Bootstrap Hotfix Scope

Arya (Architecture) | 2026-09-06 | Status: APPROVED FOR JESSE — urgent, surgical follow-up to DR2/TestFlight build 28 launch failure.

Trigger: DR2's TestFlight deployment (Build 28) is the physical-device launch proof. On Andy's existing restored/migrated install, the app does not reach a usable UI. The deployment did its job: it caught a launch-blocking regression before the diagnostic experiment could begin.

How to read this doc

Door tags: 🚪➡️🚪 = two-way door (cheap to reverse; default chosen, move on). 🚪🧱 = one-way door (expensive/irreversible; trade-offs laid out, Andy's call).

Jesse: this is a boot-path fix. Do not pull in a photo, restore-format, map, or navigation behavior theory while the app cannot start. The PR body and diff must tell the same small story.

The call

Remove database work from the pre-bootstrap diagnostic path and make database initialization single-flight.

The new DR2 root effects can call diagnosticEvent() before the root bootstrap has made the database ready. Each event currently reaches logEvent() → getDb(). getDb() caches only a completed database instance, so concurrent callers can open/migrate independently while the root's own bootstrap is also opening/migrating. If that race rejects the root bootstrap, the current root catches it and keeps dbReady false forever: a blank application.

This is a 🚪➡️🚪 implementation correction, not a storage-model or public-contract change. The hotfix eliminates the introduced launch race and ensures a future startup error is visible/retryable rather than a blank screen.

In scope

1. Single-flight database bootstrap

In src/db/database.ts:

  • Maintain one in-flight open/migrate promise in addition to the completed _db handle.
  • All concurrent getDb() callers must await that one promise and receive the same ready database instance.
  • Assign the completed _db only after migrations succeed.
  • If opening or migrating fails, clear the in-flight promise so a later retry is possible; do not retain a half-ready handle.
  • Preserve existing migration order and transaction semantics exactly. No new migration and no schema/data rewrite belongs here.
  • Update the test-only reset seam to reset both the completed handle and in-flight state.

2. Diagnostics only after bootstrap

In the root layout/diagnostic wiring:

  • Do not call diagnosticEvent() or any helper which reaches SQLite until successful database bootstrap has set readiness.
  • Mount/apply lifecycle and route diagnostics only after that point. A small child component rendered after dbReady is preferable to a pre-bootstrap root effect.
  • Keep the DR2 diagnostic events and shared timeline intact once the app is ready; this is a launch-order correction, not removal of diagnostics.
  • If retaining pathname observation needs a router hook, keep it inside the post-ready child. The root must remain able to mount without an instrumentation-side dependency on navigation context.

3. Visible startup failure and retry

Replace the silent bootstrap catch with a minimal, data-safe startup failure view:

  • Plain copy: “Frost Rocks couldn’t open its field record.”
  • A Try again action retries database bootstrap without deleting data, resetting migrations, restoring, or changing routes.
  • Log the original error to device console only; do not persist raw SQLite error strings or local paths into the diagnostic timeline.
  • The normal loading state remains unadorned while bootstrapping is in progress.

This is deliberately a recovery handle, not a new error-reporting product surface.

Explicit non-goals

  • No photo/restore write-path change, archive change, or re-restore flow.
  • No map, Trips, interactive-map, gesture, or navigation-stack change.
  • No image cache/retry/prefetch work.
  • No schema migration, data reset, database deletion, automatic repair, or user-data mutation.
  • No broad error/analytics/crash-reporting system.

Suggested implementation seams

SeamResponsibility
src/db/database.tssingle-flight open/migrate promise, failure reset, test reset
app/_layout.tsxexplicit bootstrap state + retry; defer diagnostic mount until ready
src/components/RuntimeDiagnostics.tsx (new, if useful)post-ready app-state/pathname observation only
existing DR2 diagnostic testsretain and adapt expected timing; do not weaken filtering/sanitizing assertions

Names can follow repository conventions. The important division is absolute: database readiness first; diagnostic writes second.

Acceptance evidence — required in the PR body

- cold launch to the notebook; - force-quit and relaunch to the notebook; - confirm the restored trips/encounters remain present; - open a previously restored encounter photo; and - use Share diagnostic timeline successfully.

  • Concurrency test: hold openDatabaseAsync/migration behind a deferred promise, call getDb() at least three times before it resolves, then prove one open, one migration sequence, and the same ready database returned to all callers.
  • Failure/retry test: force opening or migration to fail once; prove no completed/in-flight cache remains and the next getDb() retry can succeed.
  • Root startup test: diagnostics do not write/log before DB readiness; after readiness they start normally. A bootstrap failure renders the retry state, and retry reaches the app without mutating stored rows.
  • Regression evidence: existing DR2 timeline/filter/sanitization tests, recovery tests, npm run typecheck, npm run lint, and targeted suites all pass. Include changed-seam output in the PR body.
  • Physical TestFlight proof — required: without deleting the app, update the affected Build 28 install in place to Build 29. Then:

Record device model, iOS version, Build 28 → Build 29 upgrade, and a short screen recording. This TestFlight update is the gate; no separate simulation ritual is needed.

Review gate

🚪🧱 Not approvable without the in-place physical TestFlight upgrade from the failed Build 28 installation. A fresh simulator launch proves little here; the bug belongs at the intersection of the real migrated database, startup ordering, and the device runtime.

After PR-DR2.1: resume DR2 evidence collection. Only a captured diagnostic timeline gets to authorize a behavior-changing DR3.
