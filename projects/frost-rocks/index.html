Frost Rocks

Rock, geology, and place-based learning app. Current stage: TestFlight field pilot / multi-trip design.

Current Priority

Build multi-trip support in time for Door County so Andy can use Frost Rocks across distinct trips and run more wizard-of-oz learning pilots on a trustworthy field record.

  • Product/design: Door County multi-trip design is final; Arya’s feasibility and technical-design pass is next.
  • Architecture: Arya should reconcile that design with the existing trip scaffold, migrations, encounter model, exports, and map assumptions.
  • Engineering: Jesse follows after the design and architecture gates are clear.
  • Release reliability: Cassian stays involved before the next trip-use TestFlight build.
  • Active starting docs: Door County Multi-Trip Final Design Spec and Multi-Trip & Places Target Model.

The Finland user-zero cycle is complete. Its briefs, architecture, release history, clickable prototypes, static map assets, and trip evidence are preserved in the Finland Prototype Archive, but they no longer represent the active plan.

  • Not implemented on origin/main: first-class multi-trip selection/creation UX and the D3 AI tutor. The repo contains an early trips scaffold and dormant enrichment infrastructure; neither should be mistaken for the finished product.

What Frost Rocks Is Testing

Frost Rocks is a field notebook with memory: encounters in the world become material for later noticing, reflection, and skill development. Finland proved the capture/review substrate with one real trip. Door County is the next test: can the app support multiple named trips without losing the speed and emotional clarity of the field flow, and can that cleaner structure support repeatable WoZ tutor pilots?

The TestFlight app is evidence, not final product truth. Product decisions should be grounded in field use, exported encounter evidence, and explicit design/architecture review.

Active Workstreams

  • Multi-trip / Door County — current priority. Finalize the trip lifecycle, active-trip behavior, encounter assignment, switching, review boundaries, and migration/export expectations.
  • WoZ learning pilots — active discovery. Continue testing the evening-debrief/tutor concepts manually against real trip records before automating them.
  • AI tutor / D3 — designed, not built. Preserve the AI Tutor Design Brief, D3 Wedge Spec, three WoZ pilot logs, grounding note, and implementation plan as inputs. Re-sequence implementation behind the multi-trip decision unless Andy explicitly changes priority.
  • Release verification. Before Door County, verify the installed TestFlight build/version and regression-test capture, editing, questions, custom keywords, metadata, photo portability, and export packages on-device.
