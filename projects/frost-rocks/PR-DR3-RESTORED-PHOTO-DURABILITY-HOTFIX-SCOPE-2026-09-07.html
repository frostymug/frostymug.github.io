Frost Rocks — PR-DR3 Restored-Photo Durability Hotfix Scope

Arya (Architecture) | 2026-09-07 | Status: APPROVED FOR JESSE — bounded behavior fix authorized by Build 30 diagnostic evidence.

Trigger: Build 30's DR2 timeline establishes a real restored-photo persistence/path failure. At 01:53 a restored image was readable (6,987,357 bytes) and rendered. At 02:56 a different restored image was absent at the resolved app-managed path (exists: false, byte_count: 0, readable: false) before the native image callback failed. This is not a MapLibre rendering failure.

Build 29 → 30 is a relevant boundary. The v9 SQLite migration creates only trip_map_regions and an index; it does not alter encounter_photos, local_uri, or files. The established defect is instead the restore contract: it persists absolute, current-container file://.../Documents/photos/restore-... references rather than the app's durable relative photos/... references. Whether the upgrade truly removed a file or exposed a stale absolute reference remains unproven. The fix removes that fragile seam and proves the upgrade path.

How to read this doc

Door tags: 🚪➡️🚪 = two-way door (cheap to reverse; default chosen, move on). 🚪🧱 = one-way door (expensive/irreversible; trade-offs laid out, Andy's call).

The call

🚪🧱 New restores must write every archive photo to a permanent app-managed location and persist only its relative photos/... path. Verify the complete inventory before records are committed, retain the resulting audit after the transaction, and prove that an in-place TestFlight upgrade preserves every restored photo.

Do not add a speculative map, native-image-cache, or navigation workaround. The file probe has already ruled out the renderer as the primary failure for the captured incident.

Target storage contract

For each included archive photo, use a deterministic, collision-free relative path under the existing app-managed root, for example:

photos/restored/<restore-session-id>/<encounter-id>/<photo-id>.<extension>
  • The database stores exactly that relative value in encounter_photos.local_uri—never FileSystem.documentDirectory, a container UUID, or another absolute path.
  • Resolve it to the current document directory only at file IO/render time through the existing photo-URI resolver.
  • The restore-session directory is a final durable namespace, not a directory called “staging” and later assumed durable by accident. A temporary staging directory, if used, must be distinct and must never be persisted in SQLite.
  • Existing absolute restored rows remain read-only and render through the current compatibility resolver. Do not mass-rewrite existing field records; the affected Build 30 container is evidence, and a row rewrite cannot recreate an absent file.

In scope

1. Durable restore write and commit protocol

In the recovery restore service:

- the path is inside the intended app-managed photo root; - it exists; - byte count equals the archive byte count and is nonzero; and - a bounded read succeeds.

  • Parse and validate the archive as today.
  • Write included photo bytes to a temporary restore workspace or the final restore namespace before any recovery rows are inserted.
  • For every written file, require all of:
  • Build the photo_id → relative local_uri map only from verified files.
  • If any file fails, remove only this restore attempt's temporary/final directory, leave the existing notebook untouched, and report restore failure. Do not insert partial recovery rows and do not report success.
  • Insert the archive rows in the existing SQLite transaction, using the relative map. Preserve existing archive validation and pristine-install rules.
  • Immediately after the DB transaction, audit all restored rows by resolving their stored relative paths and re-running the same file checks. Do not emit restore_success or diagnostic_restore_committed until this audit succeeds.

Filesystem and SQLite cannot share one atomic transaction. Make the boundary explicit:

  • Before row commit, a failure rolls back by deleting only this attempt's files.
  • If the post-commit audit unexpectedly fails, do not delete assets or silently announce success. Preserve the record and emit a sanitized diagnostic_restore_post_commit_failed aggregate event; surface a data-safe restore-integrity failure. Jesse must document the exact UI/retry behavior proposed for this exceptional state before implementing it. No automatic database reset or overwrite is authorized in this PR.

2. Durable, sanitized audit trail

DR2's per-photo stage events are currently written before restoreArchiveRows(), whose transaction clears the events table. They therefore disappear from the exported timeline.

  • Accumulate per-photo verification facts in memory while writing; write the sanitized events after the row transaction succeeds.
  • Retain diagnostic_restore_photo_stage_verified (or a clearly renamed equivalent) with opaque photo ID, relative storage form, existence, byte count, and readability.
  • Add a post-commit aggregate event containing: restore-session ID, expected/included count, verified count, missing count, and unreadable count. No URI, filename, archive content, note, location, or native error string.
  • Ensure the diagnostic export allowlist and retention behavior include the new event(s).
  • A restore that fails before commit should retain a sanitized attempt/failure aggregate where the normal events table is available. It must never make diagnostics a precondition for recovery itself.

3. Upgrade and compatibility proof

  • Add a fixture representing Build 29-era restored photo rows with absolute .../Documents/photos/restore-... values. Prove the resolver still maps a valid old row to the current document directory without logging its URI.
  • Add a v8 → v9 migration fixture with restored photo rows. Assert the migration leaves every encounter_photos row, especially id, encounter_id, and local_uri, byte-for-byte unchanged. It should also prove v9 creates only its map-region schema.
  • Add a restore-service test that proves rows receive relative paths, no absolute path, and a failed file verification inserts no archive rows.
  • Add a post-commit inventory test proving every restored photo is re-resolved and audited before success is emitted. Include the event-retention regression: stage/audit evidence remains exportable after recovery's transaction has replaced archived event rows.

4. Focused operational UI

  • Preserve the existing user-visible restore result on a fully verified success.
  • On a pre-commit verification failure, show the existing data-safe restore error—never a success count.
  • For the exceptional post-commit audit failure, show plain, actionable integrity copy and allow timeline sharing. Do not add an automatic repair, repeat-restore/overwrite action, or a database reset. The exact wording is a small implementation detail; the state distinction is not.

Explicit non-goals

  • No v10 schema migration, schema rewrite, or mutation of existing restored photo rows.
  • No map, MapTiler key/configuration, offline-pack, Trips, or destination-setup change.
  • No native image retry/cache/prefetch workaround; the failed asset did not exist at the resolved path.
  • No navigation-stack repair beyond the separately deferred post-restore exit-flow work.
  • No recovery archive-format change, network upload, analytics, or raw local-path logging.
  • No attempt to repair the already compromised Build 30 container from the app. The preserved original ZIP remains the source of truth.

Acceptance evidence — required in the PR body

- install the build containing this fix and restore all 45 photos; - capture/share the successful post-commit inventory timeline (45 expected, 45 verified, 0 missing/unreadable); - update that same installation in place to the next TestFlight build that contains v9/FMT2–5 changes, without delete/reinstall; - cold launch, background/foreground, force-quit/relaunch, and visit the current-trip map/review path; - run/share a full restored-photo inventory audit after the update; and - visibly open at least the previously failed encounter and a sample across both trips.

  • Restore contract tests: happy-path included photos persist only relative photos/... URIs; each has exact expected bytes and a successful bounded read. A deliberately missing, zero-byte, wrong-size, or unreadable file leaves no archive rows and no restore files behind.
  • Transaction/audit tests: per-file verification survives the recovery transaction in the exportable timeline; restore_success/committed are impossible before a full post-commit inventory audit succeeds. The exceptional post-commit failure is visibly non-success and never triggers broad destructive cleanup.
  • Migration/compatibility tests: v8 → v9 leaves all legacy photo rows untouched; an existing valid absolute restore path remains resolvable; new rows are relative. Include changed-seam test output, not only aggregate suite output.
  • Regression: DR2 diagnostic filtering/sanitization, recovery archive validation, existing capture-photo behavior, npm run typecheck, npm run lint, and targeted test suites pass.
  • Physical TestFlight proof — 🚪🧱 release gate: using a fresh clean container and a copy of the preserved all-trips ZIP:

Record device model, iOS version, and both build numbers. The in-place TestFlight upgrade—not a clean simulator—is evidence the load-bearing seam ran.

Review gate

🚪🧱 This cannot be approved from plausible code or a green aggregate suite. The PR body must show the changed-seam output and the physical TestFlight upgrade evidence above. The story must remain “restore-path durability across upgrade”; if the diff also changes map behavior, image caching, or navigation, split it.

After PR-DR3: keep DR2 installed. If an image again reports absent after a verified relative-path restore and in-place upgrade, we have ruled out the old absolute-path contract and reopen investigation from that evidence rather than piling on guesses.
