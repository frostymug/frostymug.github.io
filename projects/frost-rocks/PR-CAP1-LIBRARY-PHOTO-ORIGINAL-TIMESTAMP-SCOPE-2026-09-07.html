Frost Rocks — FR-005 / PR-CAP1 Library Photo Capture with Original Timestamp

Arya (Architecture) | 2026-09-07 | Status: APPROVED FOR JESSE — bounded field-capture enhancement. Ship as its own PR; do not fold it into PR-DR3.

Why now

Black Hills field use produced an ordinary need: Andy already has photos in the iPhone camera roll that belong in the trip notebook. Each should become an encounter without pretending it happened at import time.

The app has a Library control today, but only on the post-camera enrichment screen—too late for an existing photo to begin an encounter. Its shared persistAsset() routine also copies a chosen JPEG and writes EXIF using new Date(), replacing original capture time with import time. That is the exact seam this PR fixes.

How to read this doc

Door tags: 🚪➡️🚪 = two-way door (cheap to reverse; default chosen, move on). 🚪🧱 = one-way door (expensive/irreversible; trade-offs laid out, Andy's call).

The call

🚪➡️🚪 Keep the center Capture action camera-first and immediate. Add a quiet, explicit Use a photo from your library escape hatch beside it in the notebook capture area. It uses the system picker, accepts one still image, creates an encounter in the current trip, and opens the same enrichment screen as a shutter capture.

🚪🧱 A library-created encounter uses the source image's capture instant and GPS location whenever iOS exposes trustworthy values—never import time or the phone's current location. Make an unmodified app-managed copy of the chosen image. If no trustworthy original time is available, say so before save and use import time; if no trustworthy source GPS is available, leave the encounter unpinned. Do not invent either value from the importing device.

No schema migration. encounters.captured_at is already the timeline/order/export authority, and the relative encounter_photos.local_uri contract is already durable. A new source taxonomy or timestamp column would be a very permanent answer to a small problem.

Product behavior

Entry and fast path

  • The existing center Capture tap still launches the camera immediately. No action sheet, confirmation, or extra tap on that path.
  • Add a low-emphasis but discoverable Use a photo from your library action adjacent to/just above Capture.
  • One selection creates one encounter in app_state.current_trip_id, then pushes /capture?id=<new-id>&mode=enrich. Six Black Hills images become six truthful moments, not a bundle with one misleading timestamp.
  • Cancellation, permission denial, or failure creates no encounter. Existing Library on enrichment may remain for additional photos, but receives the same non-mutating persistence rule.

Capture-time contract

Add a small, independently tested resolver, e.g. src/utils/importedPhotoCaptureTime.ts:

type SourceCaptureTime =
  | { capturedAt: string; tzOffsetMin: number | null; source: 'exif_original' | 'media_library' }
  | { capturedAt: null; tzOffsetMin: null; source: 'unavailable' };

Precedence:

  • Valid EXIF DateTimeOriginal (or equivalent) with an explicit parseable offset wins. Write ISO instant to captured_at, its offset to tz_offset_min.
  • Otherwise, use a finite positive MediaLibrary.getAssetInfoAsync(asset.assetId).creationTime if exposed. Write its ISO instant and tz_offset_min: null; the source timezone is unknown.
  • An unoffset EXIF civil date is insufficient to manufacture an absolute instant for a travelling field record. It may not be used when Media Library time is absent.
  • If neither source is available, show: Original photo date unavailable — this encounter will use today’s date. Then allow save with the existing import-time default and device timezone.

The resolver tolerates Expo/iOS key variants (named/numeric EXIF keys, optional offset fields, malformed dates, missing assetId, limited-library access, and asset-info failure). It must never throw the picker flow or report an original timestamp while silently using Date.now().

Source-location contract

Resolve original location from the same selected asset context, separately from the app's foreground-location service:

type SourcePhotoLocation =
  | { lat: number; lng: number; source: 'exif_gps' | 'media_library' }
  | { lat: null; lng: null; source: 'unavailable' };

Precedence:

  • A complete, finite, in-range coordinate pair from the photo's EXIF GPS is authoritative. Support the named/numeric fields and GPS reference/DMS forms Expo may surface; apply hemisphere references before validating latitude [-90, 90] and longitude [-180, 180].
  • Otherwise, use a complete, valid location reported by the selected Media Library asset when available.
  • If neither is available—because the source never recorded location, it was stripped during sharing, iOS does not expose it, or library access is limited—store lat, lng, and location_label as NULL. This is a normal successful import, not an error and not a prompt for current GPS.

No reverse geocoding belongs here. The coordinates are the source evidence; an invented or network-dependent label would merely make them less reliable.

Photo and location integrity

  • A library import only copyAsyncs into the existing photos/<id>.<extension> namespace. Retain quality: 1/no editing; never call stampJpegMetadata, writeAsStringAsync, or MediaLibrary.createAssetAsync for it. JPEG/HEIC bytes must remain unchanged and no duplicate camera-roll asset appears.
  • Camera capture retains its existing EXIF-writing and camera-roll-backup behavior. Do not refactor it casually.
  • A library-created encounter gets only the resolved source GPS. It must never call getCurrentLocation() or use the importing device's location. When source GPS is unavailable, leave lat, lng, and location_label null. Pinning a historical photo to where the phone happens to be today is a confident lie.
  • Thread resolved time, nullable source timezone, and source GPS through CapturedPhoto (or equivalent transient result) to createEncounter. Change that DB helper only enough to distinguish omitted tz_offset_min (current default) from explicit unknown null (store NULL).
  • created_at, updated_at, and encounter_photos.created_at remain actual import/write timestamps; they are audit times, not encounter time.

In scope

  • Secondary notebook library entry, one-image route, shared post-create enrich navigation, and current-trip invariant.
  • Source-specific persistence: camera behavior unchanged; library copy unmodified; best-effort single Media Library asset-info lookup without a new broad permission prompt.
  • Validated original-time and source-GPS resolvers and threading to encounter creation. Log sanitized source/resolution outcomes only (camera|library, exif_original|media_library|unavailable, exif_gps|media_library|unavailable)—never EXIF, date values, IDs, paths, filenames, or coordinates.
  • Brief unavailable-date confirmation, no date editor.

Explicit non-goals

  • No migration, backfill, export-format change, multi-select/bulk import, albums UI, duplicate detection, date editor, or batch reassignment.
  • No use of current import location, reverse geocoding, image transformation/HEIC conversion/recompression/EXIF rewrite, or camera-roll duplication.
  • No change to camera default behavior, Maps/MapTiler, trips, or PR-DR3 recovery behavior.

Suggested implementation seams

SeamResponsibility
app/index.tsxprimary immediate camera; secondary library action; library creation with source GPS or null; shared enrich route
src/services/photos.tssource-specific copy; one Media Library lookup; transient source time/location
src/utils/importedPhotoContext.tsEXIF/Media Library time + GPS precedence, timezone and coordinate parsing
src/db/encounters.tssupplied captured_at; explicit nullable timezone semantics; existing nullable coordinates
app/capture.tsxcompatible non-mutating additional library photo behavior
focused service, resolver, home/capture, and DB testschanged-seam proof

Acceptance evidence — required in the PR body

  • Resolver tests: EXIF original+offset wins; Media Library time is fallback; valid EXIF GPS wins; valid Media Library location is GPS fallback; malformed/missing EXIF, missing ID, asset-info failure, unoffset EXIF without library time, and incomplete/out-of-range GPS resolve safely to unavailable. Include exact output.
  • Persistence tests: imported JPEG and HEIC get relative photos/... paths and make no writeAsStringAsync/EXIF-stamp/createAssetAsync call; source bytes survive. Existing camera test still proves its stamping and camera-roll backup.
  • Encounter tests: library creation has historical captured_at, expected nullable timezone, import audit timestamps, and source lat/lng; it orders historically. An image without source GPS creates no pin and must never call foreground location. Unavailable time shows warning then uses import time. Camera still uses live time/location.
  • Trip invariant: while Review shows a previous trip, import a photo and prove it lands only in the persisted current trip.
  • Physical iPhone proof: select a JPEG/HEIC with a visible Apple Photos date/time and location/map pin. Compare date/time in Frost Rocks timeline/detail and coordinates on its map; both match the source. Source remains in Photos, one encounter is created, and no duplicate appears. Also test a stripped/no-date/no-location image: capture the honest time fallback warning and prove it creates no map pin. Record device, iOS, and build.
  • Run changed suites, npm run typecheck, and npm run lint; aggregate green supplements, never replaces, the seam evidence.

Review gate

🚪🧱 The question is not “does a picker open?” It is: can a photo from last week become an encounter from last week and there, without mutating it or pinning it to today’s location? No approval without resolver/persistence tests and the physical Apple Photos-to-Frost Rocks comparison. If the diff also fixes general camera metadata, adds batch import, or touches recovery storage, split it. Small blades cut cleaner.
