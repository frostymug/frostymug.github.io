Frost Rocks — Full Multi-Trip + Real Maps Implementation Plan

1. The cut we are building

In scope

- destination search; - a prefilled, adjustable rectangular offline area; - explicit download, progress, retry, and ready state; - encounter pins, including when the device is offline.

  • A Trips management surface (named and structured so Trips & Places is additive later).
  • Create, rename, configure, start, and mark over trips.
  • previous | active | upcoming trip lifecycle, with one persisted current capture trip.
  • A real interactive map for every newly created trip:
  • The existing multi-trip contract remains intact: capture goes only to the current trip; Review scopes locally and cannot redirect capture; notebook remains a cross-trip history; current/all-trip export stays explicit.
  • A migration-safe bridge for existing Finland and Door County static field maps.

Explicitly out of scope

  • Places / recurring unbounded contexts.
  • Capture with no current context or an unfiled inbox. The target model deliberately parks this with Places; do not quietly invent it here.
  • T1 preparation, T3 consolidation, or the full temporal-lenses Review IA.
  • Route planning, turn-by-turn navigation, geofences, shared maps, cloud sync, map editing after download, and a world-history map.
  • Destructive deletion of trips or field records.

Product contract carried forward

  • Capture is present-tense and singular. The shutter reads app_state.current_trip_id; no Review or map UI changes it.
  • Review time-travels. It may view any prior trip, locally scoped to that review session.
  • A trip is not active merely because its map exists. Creating and downloading an upcoming trip must not move capture away from the trip Andy is currently taking.
  • Map preparation happens before activation. A trip can be started only after its map area is ready. This is the honest version of “real map built as part of trip creation,” rather than a pretty online map that evaporates on the ferry.

2. Approved one-way-door decision

Map data + geocoding provider (🚪🧱) — approved by Andy, 2026-08-25

Decision: use MapLibre Native as the renderer and MapTiler Cloud for destination search, style, and downloadable vector tiles. MapTiler's Free plan is enabled for this work.

Why this pair:

  • @maplibre/maplibre-react-native@11.3.6 declares compatibility with the repository’s Expo 54 / React Native 0.81 / React 19 baseline. It is a renderer, not a map-data vendor, and keeps us out of a renderer-vendor lock-in.
  • One provider covers the two creation requirements: destination search and a styled tile source. The app owns the map-region and offline-pack seams, so a later provider change is contained.
  • Do not download OpenStreetMap’s public raster tiles in bulk. Their public tile service is not an offline-pack backend. That road ends in a 429 and a small amount of shame.

Implementation handoff: this approval clears PR-FMT1. Before its first EAS development build, Jesse needs the MapTiler restricted public client token for com.frostrocks.app, supplied through EAS environment configuration—not committed or copied into this document. The Free plan is the current cost ceiling; any paid-plan change is a new Andy decision.

The provider-account setup must support the planned iOS offline proof under its current terms. If that proof cannot be completed on the Free plan, stop at PR-FMT1 and bring back the measured limitation; do not quietly upgrade or ship an online-only substitute.

The originally required provider facts are:

  • a MapTiler account/project (or explicitly name an equivalent provider);
  • the intended paid/free plan and a monthly spend/usage cap;
  • permission to use its terms for offline storage on the supported platforms;
  • a restricted public client token for com.frostrocks.app (and Android package/signing identity when Android is shipped).

The token is not a secret in the cryptographic sense—the native client must receive it—but it must be restricted by application identity and injected through EAS environment configuration, never committed. A vendor account, billing terms, and offline redistribution rules are a real commitment; I will not smuggle one into a package install.

Fallback only if PR-FMT1 proves this selection cannot meet the offline contract: keep MapLibre and select a provider with (a) forward geocoding, (b) vector/raster tile URLs suitable for offline packs, (c) explicit mobile/offline terms, and (d) token restrictions. The rest of this plan does not change.

3. Architecture

3.1 The trip lifecycle and capture pointer

The existing Door County implementation already has the right base:

  • trips.state uses previous | active | upcoming.
  • app_state.current_trip_id is the only capture pointer.
  • setCurrentTrip() updates the pointer independently of Review scope.

Extend it; do not replace it with is_current on trips.

Lifecycle operations

User actionTrip state / pointer resultCapture consequence
Create tripnew row is upcoming; no pointer changestays in current trip
Configure destination and download mapremains upcoming; map becomes readystays in current trip
Start prepared tripold current becomes previous; selected trip becomes active; pointer updates atomicallysubsequent capture goes to new trip
Mark trip overshorthand only when another prepared trip is selected; perform the same atomic handoffnever leaves capture with no destination
Rename / edit datesmetadata change onlyno capture consequence

There is intentionally no standalone “end current trip and have no destination” control. That is the absent-context product problem, which belongs with Places/unfiled capture. This increment does not pretend it solved it.

3.2 Map-region persistence (🚪🧱)

Keep trips as a lifecycle record. Put map configuration and offline-pack state in a separate one-to-one table so a future Place can use the same map-region shape without a trip_id → context_id archaeology dig.

CREATE TABLE trip_map_regions (
  trip_id TEXT PRIMARY KEY REFERENCES trips(id),
  destination_label TEXT NOT NULL,
  center_lat REAL NOT NULL,
  center_lng REAL NOT NULL,
  north_lat REAL NOT NULL,
  south_lat REAL NOT NULL,
  east_lng REAL NOT NULL,
  west_lng REAL NOT NULL,
  min_zoom REAL NOT NULL,
  max_zoom REAL NOT NULL,
  style_id TEXT NOT NULL,
  provider_region_id TEXT,
  offline_status TEXT NOT NULL
    CHECK (offline_status IN ('not_requested','downloading','ready','failed','stale')),
  offline_bytes INTEGER,
  downloaded_at TEXT,
  last_error TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  CHECK (north_lat > south_lat),
  CHECK (east_lng > west_lng),
  CHECK (min_zoom <= max_zoom)
);
CREATE INDEX idx_trip_map_regions_status ON trip_map_regions(offline_status, updated_at);

Notes:

  • A rectangle is the selected offline/download area. It is intentionally not a Place boundary or a trip geofence.
  • The native map SDK owns actual tile files/cache paths. SQLite stores only durable intent and verified status, never a provider cache path that can disappear after an OS cleanup.
  • style_id and zoom range make a pack reproducible. Changing either marks a pack stale; it never silently says “ready.”
  • Coordinate validation additionally happens in TypeScript: latitude [-90, 90], longitude [-180, 180], sane maximum area/estimated-size limits, and no antimeridian-crossing region in v1. Trips spanning the antimeridian are a later, explicit map-geometry job.

3.3 Map service boundary

Create src/services/maps/ behind an interface. UI components do not call a vendor SDK directly except through a thin rendered-map adapter.

export interface MapSearchResult {
  label: string;
  center: { lat: number; lng: number };
  suggestedBounds: Bounds;
}

export interface OfflineMapService {
  searchDestination(query: string): Promise<MapSearchResult[]>;
  estimate(region: MapRegion): Promise<{ bytes: number; display: string }>;
  download(region: MapRegion, onProgress: (p: DownloadProgress) => void): Promise<void>;
  verify(region: MapRegion): Promise<boolean>;
  remove(region: MapRegion): Promise<void>;
}
  • MapTilerSearchClient implements search over HTTPS using the restricted client token.
  • MapLibreOfflineService implements pack creation, progress, verification, and removal with the pinned native SDK.
  • MapRegionRepository is the SQLite layer; it translates native download outcomes into the durable offline_status state machine.
  • The FieldMap screen takes a trip + region + encounter pins. It knows no provider names, token, or SQL.

This is deliberate: renderer and map data may evolve independently, and future Places can reuse the region record.

3.4 Existing Finland / Door County bridge

Do not force a giant redownload or change existing field behavior during migration.

  • Preserve map_descriptor_key and the static Finland/Door County assets for existing trips.
  • Map resolution order is: verified trip_map_regions pack → legacy static descriptor → honest “map not prepared” state.
  • The Trips screen offers existing trips an explicit Set up interactive map action using the same destination/area/download flow. It does not delete the legacy asset.
  • New trips never receive a static descriptor. They require a prepared interactive map before activation.

This makes the real-map model the forward path without turning an upgrade into a 300 MB surprise at launch.

3.5 Native build implications

MapLibre is native code. Expo Go is not a test target for this increment.

  • Add the library/config plugin and any iOS/Android native configuration required by the pinned release.
  • Build a development client and EAS preview build after PR-FMT1; a JavaScript-only OTA update cannot introduce the SDK.
  • Keep the existing location permission. Add no background-location permission: maps display captured pins and current foreground location only if it already exists in scope.
  • Keep MapTiler token configuration in EAS environment variables exposed as a deliberately named public client setting at build time. Restrict it on the provider side.

4. User flows to implement

4.1 Create and prepare a trip

  • Open Trips from the reserved fifth navigation slot.
  • Tap Create trip.
  • Enter title (required) and dates (optional).
  • Search a destination. Selecting a result sets a suggested center and rectangle.
  • Adjust the rectangle with map handles / a visible viewport control. Show the selected area, zoom range, and estimated download size.
  • Tap Download field map. Persist the trip first as upcoming, then run the resumable download.
  • Show progress, cancel, retry, and a plain failure explanation. On verified completion, show Map ready.
  • Tap Start this trip only when ready. Confirm the handoff copy names the outgoing and incoming trips; then make the state/pointer change in one transaction.

The creation flow defaults to upcoming, even if the departure is tomorrow. “Start” is a separate, clear action because it changes where every shutter press goes.

4.2 Manage trips

  • Group rows as Current, Upcoming, and Previous. (Current is a presentation label for the active pointer; persisted vocabulary remains active.)
  • Upcoming: edit title/dates/destination, redownload map, start when ready.
  • Current: rename/edit dates, inspect map status, create/prepare the next trip. No standalone end action.
  • Previous: rename/edit dates, review, export, and optionally set up an interactive map for history.
  • No delete control in this increment. The export and historical record are more important than tidying a list.

4.3 Map screen

  • Current trip map opens as an interactive MapLibre map with its verified offline pack and the trip’s pins.
  • Pin interaction continues to deep-link to the encounter/review flow without changing review or capture scope.
  • When online, the map may fetch tiles outside the downloaded area only if the provider allows it; no readiness claim may rely on that.
  • When offline, the selected region and pins must render. Panning beyond the offline region shows ordinary unavailable map area, never Finland or an invented base map.
  • The compact notebook card displays the prepared map region and pins. It remains current-trip only; cross-trip map is out of scope.

5. Migration plan

Migration v9 — map-region table only

Add trip_map_regions and its index. Do not alter encounters, questions, photo records, events, trips.state, or app_state.current_trip_id.

Existing-data invariants

  • Finland and Door County rows, ids, states, and map descriptors remain unchanged.
  • Every encounter/photo/question/keyword/event remains byte-for-byte equivalent except migration bookkeeping.
  • Current pointer remains Door County (or the actual persisted current trip on a later device).
  • A v8→v9 upgrade with no map preparation works normally through the legacy static descriptor.
  • A repeat/recovery of migration v9 is inert (CREATE TABLE IF NOT EXISTS only).

Map-status recovery

On app start and on entering Trips:

  • Read all regions marked downloading or ready.
  • Ask the native service whether the pack exists and is complete.
  • downloading with no live native task becomes failed with recoverable copy, not an eternal spinner.
  • ready missing its native data becomes stale; offer re-download before activation/use as a real map.

No automatic background redownload. It could consume a hotel’s Wi-Fi while looking very industrious and being exactly the wrong thing.

7. Manual field matrix — non-negotiable release gate

Run on a physical TestFlight/preview build, not a simulator alone:

  • Upgrade a Finland + Door County device database. Verify notebook, review shelf, static-map bridge, capture, and both exports.
  • Create a future trip while Door County is current. Verify capture still writes Door County.
  • Search destination, adjust an area, inspect estimated size, download over Wi-Fi, and confirm ready status.
  • Force quit, disable network, relaunch, open the prepared map, pan/zoom within its selected region, and open an encounter pin.
  • Start the prepared trip. Verify old trip becomes previous, new trip active/current, and a camera-first capture writes to the new trip.
  • Open Finland in Review; then capture. Verify capture remains on the new active trip.
  • Induce an interrupted download. Verify retry works and unready trip cannot start.
  • Export current and all trips. Verify scope, photos, and existing WoZ-compatible v3 current bundle.
  • Check disk usage before/after a pack and after its explicit removal in a development test. No silent cache growth claim without evidence.
