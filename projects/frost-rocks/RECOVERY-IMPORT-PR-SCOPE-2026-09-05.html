Frost Rocks — PR-DR1 Recovery Import Scope

Arya (Architecture) | 2026-09-05 | Status: APPROVED FOR JESSE — recovery slice inserted after verified PR-FMT1 and before PR-FMT2.

Trigger: deleting Frost Rocks from an iPhone removes its sandboxed SQLite database. Andy holds a complete frost-rocks-export-all archive and needs a reliable way to recover it into a fresh install.

How to read this doc

Door tags: 🚪➡️🚪 = two-way door (cheap to reverse; default chosen, move on). 🚪🧱 = one-way door (expensive/irreversible; trade-offs laid out, Andy's call).

Jesse: the PR must show evidence that the restore seam actually ran. A green aggregate suite is not evidence that a zip can survive a delete-and-reinstall recovery. The PR story and diff must agree.

The call

Ship one narrow, self-service restore path for the existing all-trips archive:

> Restore from Frost Rocks backup → choose archive → validate → restore a fresh app → show a truthful result.

This accepts exactly frost-rocks-export-all, export_schema_version: 1. It is not a generic importer, a merge tool, or cloud sync. Those are different beasts with different teeth.

The archive format is already an external durable contract, so accepting it as recovery input is a 🚪🧱 decision. The small supported surface is deliberate: it gets Andy's record back without inventing conflict resolution, cross-device sync, or format archaeology.

In scope

Entry and guard

  • Add Restore from Frost Rocks backup to the Export screen, with direct, sober copy that restoration is available only before recording new data on this install.
  • Use the platform document picker; copy the selected archive into app-controlled temporary storage before reading it.
  • Enable the action only for a pristine install: no encounters, photos, questions, keywords, or user-created trips. The app's migration-seeded Finland/Door County shell is allowed and is replaced during recovery.
  • If any user data exists, do not offer an in-place restore. Tell the user to export that record first; this PR intentionally has no merge or overwrite mode.

Accepted archive and validation

Validate everything before a database write:

  • zip is readable and contains manifest.json, encounters.json, and the files declared by the manifest;
  • manifest format is frost-rocks-export-all and schema is exactly v1;
  • trip ids are unique; encounter ids are unique; every encounter references an archive trip; and exactly one archived trip is active;
  • enum/field values match the current database contract (including review state, uncertainty, themes/keywords, and questions where present);
  • each included photo path is a normalized relative photos/<encounter-id>/... path, appears once, is inside the archive, and belongs to the declared encounter;
  • missing photos explicitly marked status: 'missing' remain missing and are counted in the result; an undeclared/missing included photo rejects the archive; and
  • malformed, unsupported, incomplete, or oversized archives fail with a useful message and leave the install unchanged.

Keep parsing/validation pure and fixture-driven. Do not trust zip entry paths or use them as filesystem destinations directly; path traversal is a very old trick wearing a new coat.

Restore execution

  • Extract/copy validated included photos into a unique app-controlled restore directory.
  • In a single SQLite transaction, replace only the pristine migration-seeded shell and insert archive trips, encounters, photo rows, themes/keywords, questions, and exported event rows with their archived ids and timestamps intact.
  • Set app_state.current_trip_id from the archived active trip. Preserve previous | active | upcoming states exactly.
  • Commit only after every database row can refer to its staged local photo URI. On any pre-commit failure, remove the staged directory and leave the database untouched.
  • After success, render a result with trip, encounter, restored-photo, and explicitly-known-missing-photo counts. Do not claim a complete photo restore when the source archive marks one missing.

The imported field record is authoritative. Do not recreate enrichment jobs, native map packs, transient UI state, or native camera-roll asset ids: none is safely portable, and none is needed to recover the notebook. Static Finland/Door County map descriptors continue through the existing trip data; future MapLibre offline packs are per-device cache and must be prepared again.

Result and diagnostics

  • Success view: named archive, number of trips/encounters/photos restored, known missing-photo count, and return-to-notebook action.
  • Failure view: plain cause and a retry action; no partial-data success state.
  • Log restore_start, restore_success, and restore_failure with archive schema/version and aggregate counts only—never file paths, notes, or other field-record content.

Explicit non-goals

  • Current-trip frost-rocks-export v3 import or conversion.
  • Merge, overwrite, duplicate detection, selective-trip restore, or restore into a non-pristine record.
  • iCloud/CloudKit/backend backup, cross-device sync, scheduled backup, or automatic import on app launch.
  • Restoring native MapLibre offline packs, cached tiles, queued enrichment work, camera-roll linkage, or UI/navigation state.
  • Altering the export format. Existing current-trip and all-trips exports must remain byte-compatible except for ordinary generated timestamps/paths.

Implementation shape

Suggested seams (names may adjust to repository conventions):

SeamResponsibility
src/services/recovery/archive.tsread zip, parse and validate the v1 archive into typed data; no SQL or React
src/services/recovery/restore.tsstage files, coordinate the atomic database restore, clean failed staging
src/db/recovery.tspristine-install check and transactional inserts/current-pointer write
app/export.tsxfile-picker entry, confirmation, progress, success/failure states
tests/fixturessmall all-trips archive fixture with Finland + Door County, multiple photos, questions, keywords, events, and one known-missing photo

Reuse the existing archive/relative-photo-path conventions and zip dependency where possible. A new native dependency is not justified unless Expo's supported document-pick path requires it.

Acceptance evidence — required in the PR body

  • Pure validation tests: accept the v1 fixture; reject wrong format/version, corrupt zip/JSON, duplicate ids, dangling trip/photo references, traversal path, absent included photo, and more than one/no active trip.
  • Database round-trip test: export a fixture containing Finland + Door County records, wipe to the migration-seeded pristine shell, restore, then compare archive-backed rows field-for-field: trips/states/current pointer, encounters, photos, themes/keywords, questions, and events. Account explicitly for only the new restore telemetry event(s).
  • Rollback test: induce a staged-photo or SQL failure and prove no encounter/trip/user-data rows were added and no staged directory remains.
  • Guard test: a non-pristine database cannot enter the restore path and is not modified.
  • Physical-iPhone proof: export all trips → save the zip outside Frost Rocks (Files/iCloud) → delete the app → install the recovery build → restore → inspect Finland and Door County records and several restored photos. The PR body includes the counts from both ends and a short recording or reproducible steps.
  • npm run typecheck, npm run lint, and the targeted restore tests.

Sequencing

PR-FMT1 is now verified. Execute PR-DR1 next, then resume PR-FMT2 unchanged. PR-DR1 does not depend on the FMT2 map-region migration and must not pull map lifecycle work into its diff.

Before the device test, keep Andy's existing zip outside the Frost Rocks sandbox and make a second copy. The first successful restore is recovery, not an excuse to tempt the gods twice.
