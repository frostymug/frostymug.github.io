Door County Multi-Trip — Implementation Plan

Arya (Architecture) | 2026-08-01 | Status: READY FOR JESSE — Andy-approved product decisions locked; technical decisions below are mine unless flagged 🚪🧱. Source design spec: tracks/multi-trip/DOOR-COUNTY-MULTI-TRIP-DESIGN-SPEC.md (Izzy, 2026-08-01, FINAL). Repo baseline verified: aspen-frost/frost-rocks main@7f6c449, migrations at v6.

How to read this doc

Door tags: 🚪➡️🚪 = two-way door (cheap to reverse; default chosen, move on). 🚪🧱 = one-way door (expensive/irreversible; trade-offs laid out, Andy's call).

Jesse: build in PR order (§6). Each PR ships with the acceptance evidence listed under it — that's gate #1 of my review. Diff must match the PR body (gate #2). Don't skip the migration snapshot test in PR-DC1; that's the one that protects Andy's live Finland data.

---

1. TL;DR

Turn Frost Rocks from a single-hard-coded-trip app into a two-trip app for Door County, per Izzy's FINAL 2026-08-01 spec. Behind-the-scenes migration seeds Door County 2026 as current/active and marks the existing Finland 2026 row previous. Notebook shows one continuous cross-trip timeline with a labelled divider. Review gets a dropdown shelf that changes review scope only — never capture. Map is scoped to current trip and driven by a per-trip descriptor (Door County asset bundled). Export UI offers two labelled scopes; the current-trip bundle stays byte-identical to today's format (WoZ pilots consume it). No Trips management tab. No Places. No MapLibre. Six sequenced PRs (DC1–DC6), each independently mergeable, each with acceptance evidence at the changed seam.

3. Technical decisions

3.1 Current-trip persistence — app_state single-row settings table (🚪🧱)

Options considered:

  • (a) is_current boolean column on trips.
  • (b) app_state(key, value) table with a current_trip_id row.
  • (c) Derive from state + dates.

Rejected (c): brittle. The target model (§5) explicitly warns against a hard single-"active"-pointer assumption because near a trip boundary you're simultaneously T3-of-previous and T1-of-upcoming. Deriving "current" from state means those two roles can't coexist.

Rejected (a): puts "which trip is current" onto the trips table as an attribute of a trip. That's exactly the coupling the target model (§2) tells us to avoid — when we generalize trip_id → context_id (trip | place | unfiled), we'd have to migrate is_current off trips and onto whatever contexts becomes.

Picked (b): app_state(key TEXT PRIMARY KEY, value TEXT NOT NULL, updated_at TEXT NOT NULL). Key current_trip_id. Reasoning:

  • Cleanly separates "which trip is the current capture context" (an app-level pointer) from "trip metadata + lifecycle state" (properties of the trip row).
  • When the trip→context generalization lands later, the pointer becomes current_context_id (+ optional current_context_kind) without a trips-table migration.
  • Doubles as a home for other transient app-level state we'll want (last review scope, "seen this notice", door_county_seeded idempotency marker) without more schema churn.

Why 🚪🧱: picking (a) is easy to un-pick (you can migrate off it), but picking it shapes everything Jesse writes after: every "which trip?" question gets answered by asking a trip row instead of asking the app. That's a subtle direction to reverse. This is the target-model-preserving choice.

3.2 Trip state — explicit state column, invariant enforced in code (🚪➡️🚪)

Add trips.state TEXT NOT NULL DEFAULT 'active' CHECK (state IN ('previous', 'active', 'upcoming')). Matches target model §5 vocabulary. upcoming is inert in this release (no UI, no behavior) — the column exists so the vocabulary is durable and PR-DC5 for Trips & Places later is additive.

Do not enforce "exactly one active at a time" in schema (partial unique index). The target model's in-between case (T3-of-previous + T1-of-upcoming both running near a boundary) rejects the hard-single-active constraint. Enforce transactionally in setCurrentTrip(): when we point at a new current trip, the previous current flips to previous. That's a code invariant Door County needs; the target model can relax it later.

Two-way door: if I'm wrong, we add the partial unique index later.

3.3 Migration ladder — v7 (schema) + v8 (data seed), both additive (🚪🧱)

Ship as separate migrations, in order. Splitting keeps each one's failure mode legible.

v7 (schema-only, additive):

ALTER TABLE trips ADD COLUMN state TEXT NOT NULL DEFAULT 'active'
  CHECK (state IN ('previous', 'active', 'upcoming'));

ALTER TABLE trips ADD COLUMN map_descriptor_key TEXT;

CREATE TABLE app_state (
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL,
  updated_at TEXT NOT NULL
);

No data touched. Reversible in the trivial sense (dropping the column + table would restore v6), and every existing trip picks up the default state='active', which we correct in v8.

v8 (data seed, idempotent): run as a versioned migration (not app-startup code), so it runs exactly once per install per version:

  • Idempotency guard. If app_state.door_county_seeded = '1', return early. (Belt + suspenders — versioned migrations already guarantee once-only, but this survives a wonky re-run.)
  • Seed Door County. INSERT INTO trips (id, title, start_date, end_date, created_at, state, map_descriptor_key) VALUES (<uid>, 'Door County 2026', NULL, NULL, <nowIso>, 'active', 'door-county-2026');
  • Demote everything else. UPDATE trips SET state = 'previous' WHERE id != <door_county_id>; — this handles Andy's Finland row, a fresh install (no-op), and defensively also handles a renamed Finland (title-based lookup would miss). Do not hardcode Finland by title.
  • Backfill Finland's map descriptor key. UPDATE trips SET map_descriptor_key = 'finland-2026' WHERE title = 'Finland 2026' AND map_descriptor_key IS NULL; — title-based here is acceptable because it's a best-effort recovery of the field-map hookup, not a correctness invariant. Miss → Finland map falls back to the honest empty state per spec §3.4. That's fine.
  • Set the current pointer. INSERT INTO app_state (key, value, updated_at) VALUES ('current_trip_id', <door_county_id>, <nowIso>);
  • Mark seeded. INSERT INTO app_state (key, value, updated_at) VALUES ('door_county_seeded', '1', <nowIso>);

Trip start/end dates left NULL for Door County (Andy confirmed silent transition; there's no UI to set them). If Andy wants dates displayed later, add via renameTrip-style helper — nothing in this release renders them.

Why 🚪🧱: migration version numbers are permanent. Getting v7/v8 wrong on TestFlight leaves Andy with a dead or duplicate-tripped install. This is the one place in the plan where the honest answer is "test it against a real DB snapshot before merge."

3.4 Map descriptor seam — code registry + trips.map_descriptor_key pointer (🚪➡️🚪)

Data: trips.map_descriptor_key TEXT (nullable). NULL → no map. Migration v8 sets finland-2026 and door-county-2026. Code: src/config/mapDescriptors.ts:

export interface FieldMapDescriptor {
  key: string;                       // registry lookup key
  label: string;                     // human label (e.g., "Door County 2026")
  compactCopy: string;               // notebook compact-map caption
  image: ImageSourcePropType;        // bundled asset
  imageWidth: number;                // logical pixel dims
  imageHeight: number;
  boundsNW: { lat: number; lng: number };
  boundsSE: { lat: number; lng: number };
}

export const MAP_DESCRIPTORS: Record<string, FieldMapDescriptor> = {
  'finland-2026': { /* extracted from current FinlandMap + mapProjection constants */ },
  'door-county-2026': {
    key: 'door-county-2026',
    label: 'Door County 2026',
    compactCopy: 'DOOR COUNTY FIELD MAP',
    image: require('@/assets/map/door-county-map.png'),
    imageWidth: 1024,
    imageHeight: 1096,
    boundsNW: { lat: 45.50, lng: -88.22 },
    boundsSE: { lat: 44.40, lng: -86.78 },
  },
};

export function resolveDescriptor(key: string | null): FieldMapDescriptor | null {
  if (!key) return null;
  return MAP_DESCRIPTORS[key] ?? null;
}

Rename FinlandMap → FieldMap(props: { descriptor: FieldMapDescriptor, pins: Pin[] }). mapProjection becomes projectLatLng(coord, descriptor.imageWidth, descriptor.imageHeight, descriptor.boundsNW, descriptor.boundsSE) — bounds as inputs, not constants. Existing Finland behavior renders byte-identical because it's the same numbers, just plumbed through a descriptor.

Why 🚪➡️🚪: the descriptor shape is invented here and can evolve freely — the "seam" the target model wants preserved is just "one place resolves current trip → map." That seam is resolveDescriptor(currentTrip.map_descriptor_key), called from app/map.tsx. MapLibre later swaps the descriptor kind ("static image" → "tile source") without touching callers. If I got the field shape wrong, we edit the interface — not the world.

3.5 All-trips timeline query — new dedicated read (🚪➡️🚪)

Add listAllEncountersAcrossTrips(): Promise<EncounterWithMeta[]> in src/db/encounters.ts. Reverse-chronological by captured_at DESC across the whole encounters table, joined to trips for the divider metadata. Do not client-merge two listEncounters(tripId) results — that violates spec §4 ("Do not fake this by merging client lists without a stable ordering rule.").

Notebook (app/index.tsx) uses listAllEncountersAcrossTrips() and passes the flat list to groupByEventWithinDay() — but with one wrapper step: before day-grouping, split the list at trip boundaries so each contiguous trip segment groups independently and gets its divider header. Suggested helper groupByTripThenDayThenEvent(encounters, trips) in src/utils/timeline.ts. Preserves the existing within-day event grouping; adds trip-level segmentation on top.

Filter interaction: theme filter applies to the flat list before trip segmentation. Empty states distinguish:

  • No encounters at all → "No encounters yet."
  • No encounters match filter (any trip) → "No encounters match this theme." Filter chip visible.

3.6 Export scope — new all-trips builder; current-trip bundle unchanged (🚪🧱)

Andy confirmed: current-trip export byte-identical. WoZ pilots consume frost-rocks-export schema v3; that contract is frozen.

Current-trip export (unchanged):

  • Entry point: buildExportBundle(trip: Trip) — no signature change.
  • Called with getCurrentTrip() result (Door County).
  • Format tag frost-rocks-export, schema v3.
  • Bundle name frost-rocks-export-<timestamp>.zip.

All-trips export (new):

``json { "format": "frost-rocks-export-all", "export_schema_version": 1, "generated_at": "...", "trips": [ { "id": "...", "title": "Door County 2026", "state": "active", "start_date": null, "end_date": null, "encounters": [ { "id": "...", "photo_count": 3, "photos": [...], "question_ids": [...] } ] }, { "id": "...", "title": "Finland 2026", "state": "previous", ..., "encounters": [...] } ], "files": { "encounters": "encounters.json", "events": "events.json", "journal": "journal.md" } } ``

  • New entry point: buildAllTripsExportBundle(trips: Trip[]) in src/services/exporter.ts.
  • New pure builders in src/db/export.ts: buildAllTripsManifest, buildAllTripsEncountersExport, buildAllTripsJournalMarkdown.
  • Format tag frost-rocks-export-all, schema v1.
  • Manifest top-level shape:
  • encounters.json is a flat array; every encounter carries trip_id. No trip-scoped subdirectory for encounters. Photos remain at photos/<encounter_id>/<photo_id>.<ext> (already keyed by encounter, not trip — no collisions).
  • journal.md uses trip sections at the top level (# Door County 2026 (active) / # Finland 2026 (previous)), day sections within. Not interleaved.
  • Bundle name frost-rocks-export-all-<timestamp>.zip.

Why 🚪🧱: once we ship a manifest shape and Andy hands it to anyone (consultant, future WoZ variant, an archival step), we own that format. Getting the top-level structure right now — trips[] with nested encounter pointers, encounters flat, trip identity preserved on every encounter — is worth the ten minutes to think about.

3.7 Review scope memory (🚪➡️🚪)

Review's trip scope is component-local state in app/review.tsx. On every nav-initiated entry (bottom-nav tap, deep link from map/timeline), it resets to getCurrentTrip() — Door County. Do not persist review scope across sessions. Spec §3.3: "resets to current Door County on a fresh nav-initiated Review visit." Direct links (map pin, encounter row) open that specific encounter regardless of shelf state (that's not a scope selection, it's a target).

The invariant that matters: selecting a shelf row calls the review scope setter only, never setCurrentTrip(). This gets a dedicated test in PR-DC3.
