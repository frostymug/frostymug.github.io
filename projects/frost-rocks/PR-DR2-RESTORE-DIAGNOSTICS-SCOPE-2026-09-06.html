Frost Rocks — PR-DR2 Photo-Preservation / Navigation Diagnostics Scope

Arya (Architecture), amended by Cassian (Reliability) | 2026-09-06 | Status: APPROVED FOR JESSE — AMENDED — diagnostic follow-up to TestFlight build 27 field evidence.

Trigger: After Map → encounter navigation in build 27, app-managed encounter images became unavailable across Notebook, Encounter, and Review; the records remained intact. Export then had no usable escape after restore was correctly denied on the populated install. A prior restore may be relevant, but it is not a proven prerequisite. The sequence is currently not reliably reproducible. This PR captures evidence on the physical TestFlight device before anyone “fixes” an attractive theory.

How to read this doc

Door tags: 🚪➡️🚪 = two-way door (cheap to reverse; default chosen, move on). 🚪🧱 = one-way door (expensive/irreversible; trade-offs laid out, Andy's call).

Jesse: the changed seam is diagnostic observability plus a minimal, working Export exit. It is not photo persistence or speculative navigation behavior. The PR body must show the diagnostics running through the controlled preservation path. A green test suite or console output from a simulator is not that evidence.

The call

Ship one small diagnostic build that records a sanitized, durable timeline for the app-managed-photo → map → review path and lets Andy share that timeline from Export after a failure or relaunch.

🚪➡️🚪 Do not rewrite restore file layout, add image-cache workarounds, alter map gestures, change stack behavior, or add a speculative navigation fix in this PR. Restore works in ordinary use. The job here is to distinguish, on the device that failed:

  • the app could no longer find/read an app-managed image file;
  • the native image renderer failed despite a readable file; or
  • the navigation/gesture state was the failure while the file remained sound.

In scope

1. App-managed photo probes

Add a small diagnostic helper, kept out of rendering/layout code, which records only the following facts:

MomentEventRequired data
A restored photo is stageddiagnostic_restore_photo_stage_started, diagnostic_restore_photo_stage_verifiedopaque photo id; storage form (relative / absolute-current-container); file exists; byte count; readability result
A restore transaction completesdiagnostic_restore_committed, diagnostic_restore_rolled_backopaque restore-session id; aggregate count only
Immediately before Map opens / a pin navigates / Review focuses / Review returns / app relaunchesdiagnostic_photo_file_probecheckpoint; opaque encounter/photo id; source (restored / captured / unknown); file exists; byte count; readability result
A Review or Encounter Detail image is about to renderdiagnostic_photo_render_probesurface (review / encounter_detail); opaque encounter/photo id; source; file exists; byte count; readability result
Native image begins / succeeds / failsdiagnostic_photo_load_start, diagnostic_photo_load, diagnostic_photo_errorsurface; opaque encounter/photo id; source; failure class only
  • Probe all app-managed encounter photos involved in the Map → Review path, not merely restore-marked rows. Record source where it is known; the field incident affected every surface and a restore is not a proven prerequisite. Do not probe unrelated gallery/field-capture activity.
  • Restore observation must accurately reflect durability: emit stage_started, then stage_verified after the write, then restore_committed or restore_rolled_back only after transaction outcome. Do not imply a staged asset is a committed asset.
  • A file probe must distinguish exists, nonzero byteCount, and readable (a bounded, non-content-retaining read). Existence alone does not distinguish a renderer failure from an unreadable/corrupt file.
  • Diagnostics are best-effort and failure-isolated: a failed file probe, event write, JSON build, or share sheet must never fail or alter restore, navigation, rendering, records, or assets.
  • Bound the durable timeline to the most recent 500 events or 7 days, whichever is reached first; pruning must affect diagnostic events only.
  • diagnostic_photo_error must not retain the native error string, URI, file path, note, location, or image bytes. Use a fixed/sanitized class such as native_image_error.
  • Do not log raw local URIs anywhere. Opaque existing encounter/photo ids are sufficient to correlate events with the archived record.

2. Route, map, and lifecycle timeline

Record enough chronology to correlate the exact field sequence:

  • diagnostic_route: Expo Router pathname and transition kind (focus / blur or equivalent); no raw query string.
  • diagnostic_app_state: active, background, or inactive transition.
  • diagnostic_map_pin_open: opaque encounter id, emitted before the map pin navigates to Review.
  • diagnostic_photo_file_probe at the lifecycle checkpoints listed above, including after relaunch.

Keep existing map_zoom_start, map_zoom_end, review_open, restore_*, and image-zoom events intact. The new events supplement them; no migration is needed because the events-table type constraint was removed in schema v3.

3. Shareable diagnostic timeline

On Export, add a sober secondary action:

> Share diagnostic timeline

It writes and shares a small JSON file containing only restore_ and diagnostic_ events, in timestamp order. It must be available after a restore and after force-quit/relaunch; it must not require building a full export first.

The JSON includes a format/version header and events. It excludes notes, locations, raw paths/URIs, image bytes, and unrelated usage events. If sharing is unavailable/fails, surface the existing plain export error treatment.

Export must always expose a working Index/Back action, including after restore is denied or sharing fails. Sharing is evidence egress; it is not a substitute for being able to leave the screen.

4. TestFlight capture instructions

Include these exact reproduction/capture steps in the PR body and in the Export-screen helper copy or a concise linked note:

  • Use a fresh install and a copy of the preserved all-trips ZIP; restore once. Use at least two app-managed photos when the fixture permits.
  • Record the pre-map diagnostic file facts, then open the active trip's map; pan/zoom; tap the same pin that failed if known; wait for Review to settle; return; and force-quit/relaunch.
  • At every checkpoint, confirm both visible rendering and unchanged file existence, byte count, and readability for the selected photos.
  • If a photo is absent or navigation misbehaves, do not restore again or delete the app. Use Export's Index/Back action as needed and Share diagnostic timeline. If Export is not reachable, force-quit/relaunch, then share it from Export.
  • Record the phone model, iOS version, TestFlight build number, and a screen recording if practical. Those are release-test evidence, not event payload.

Explicit non-goals

  • No restore-format, archive-parser, photo-storage, SQLite schema, or migration change.
  • No image retry/cache/prefetch implementation.
  • No speculative map gesture, map rendering, route-stack, or image-cache behavior change. A minimal Export Index/Back escape is explicitly in scope.
  • No generic analytics service, remote telemetry, crash reporter, network request, or collection of field-record content.
  • No full-export behavior change and no repeat restore/overwrite mechanism.

Suggested implementation seams

SeamResponsibility
src/services/recovery/restore.tsemit stage/verification/commit-or-rollback events without changing restore semantics
src/services/diagnostics.ts (new)sanitize event payloads; testable file probe and diagnostic-event helpers
app/_layout.tsxapp-state and pathname transition observation
app/map.tsxpre-map and map-pin file/navigation probes before router.push
app/review.tsx, app/encounter/[id].tsxlifecycle/render probes plus Image load/start/error callbacks for app-managed photos in the affected path

src/types/index.tsadditive event-type union entries

Names may adapt to repository conventions. Keep the filter/test logic centralized; do not duplicate URI or error-sanitizing rules across screens.

Acceptance evidence — required in the PR body

- diagnostic exporter includes only allowed event families, is ordered, and excludes unrelated events; - native-image error payload is sanitized (no raw message/URI); - photo probe distinguishes absent, zero-byte, and readable nonzero files; - captured, restored, and unknown source values are handled without raw URI exposure; - diagnostic failure is isolated from its calling operation; retention removes diagnostic events only.

  • Targeted unit tests:
  • Screen tests: Review and Encounter Detail emit probe → load on an app-managed-photo happy path and probe → sanitized error on the error callback. Map-pin press emits its event before navigation. Export's Index/Back action works after a denied restore and after a share failure.
  • Restore seam test: a fixture restore produces stage → verification → committed or rolled-back events with only permitted aggregate/file facts. Existing recovery validation/rollback tests remain green.
  • Physical-iPhone preservation proof: clean install → restore preserved ZIP → record pre-map file facts → map pan/zoom → pin → photo visibly loads → return → force-quit/relaunch → photo visibly loads. At each checkpoint, the selected photos retain their existence, byte count, and readability. Share the resulting timeline. The PR body includes exported JSON and device/build metadata, with raw identifiers redacted from the PR if necessary.
  • npm test -- --runInBand <targeted suites>, npm run typecheck, and npm run lint.

Review gate

🚪🧱 Two distinct gates apply. Code may be approved, merged, and built for a narrowly limited TestFlight diagnostic cohort once the static PR requirements above pass. TestFlight is the physical-device validation lane. The unit/component tests prove our probes emit; only the TestFlight device run proves the actual renderer, file sandbox, map gesture, and navigation seams executed together.

Release boundary: DR2 is diagnostic-only. Passing its TestFlight capture procedure does not retroactively clear build 27, permit wider exposure, or close the incident. PR-DR3 requires a reproduced causal trace, a behavior fix, regression coverage, and physical-device proof on the affected flow.

Expected outcome: the controlled run gives us a preservation baseline timeline. A subsequent failure gives us a bounded causal trace. Only then does PR-DR3 get to change behavior.
