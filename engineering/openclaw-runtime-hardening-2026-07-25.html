OpenClaw Runtime Hardening Recommendations - 2026-07-25

Status: Review draft for Andy Owner: Aspen Scope: Main Lightsail OpenClaw host, cron jobs, docs publish workflow, gateway reliability Incident reviewed: 2026-07-25 memory exhaustion and host reboot

Executive Summary

The 2026-07-25 host incident was most likely caused by the docs-nightly-review-publish OpenClaw cron job exhausting memory and swap, followed by partial host degradation that a gateway restart could not repair.

The immediate recommendation is to disable or replace the agent-turn nightly docs cron with a deterministic shell publish job, then reintroduce agent review in a lower-frequency or manually-triggered form. The broader recommendation is to add hard resource boundaries around OpenClaw cron work and either scale the Lightsail instance or reduce concurrent background work.

This is not primarily a docs-site problem. The docs publish pipeline is lightweight when run directly. The risky part is the nightly autonomous agent review wrapped around it: broad context, tool access, model/tool child processes, long timeout, and unclear cleanup after timeout.

Recommendations

1. Disable The Agent-Turn Nightly Docs Cron Immediately

Why:

The nightly job has already demonstrated it can push the host into memory exhaustion. Disabling it stops the repeat-failure path while preserving every manual docs publish path.

How:

openclaw cron disable c76b1072-9591-455f-8d06-c69de4346d18
openclaw cron show c76b1072-9591-455f-8d06-c69de4346d18

Expected result:

enabled should be false.

Operational effect:

Andy will stop receiving nightly autonomous docs-review summaries until the safer replacement exists. Manual publish still works.

2. Use The Deterministic Docs Publish Pipeline For Routine Publishing

Why:

The deterministic publish path does not need an agent turn, long context, model calls, or broad autonomous exploration. It runs the known scripts, builds the static site, checks links, publishes, and logs output.

How to run manually:

cd /home/ubuntu/.openclaw/workspace/project-viewer
./scripts/nightly-update.sh

What it does:

  • Runs scripts/update-project-pipeline.js
  • Builds the static docs viewer
  • Checks internal links
  • Publishes to frostymug/frostymug.github.io
  • Writes a log under project-viewer/logs/nightly-YYYY-MM-DD.log

Operational effect:

Docs remain publishable without exposing the host to an autonomous review loop every night.

3. Replace The Nightly Agent Cron With A Command Cron

Why:

If nightly publishing should remain automatic, the job should be a command job with bounded output and timeout, not an agent job. Agent review can happen separately and less often.

Implementation option:

openclaw cron add \
  --name docs-nightly-deterministic-publish \
  --description "Nightly deterministic docs publish: audit, build, link-check, publish, and log output without an agent review turn." \
  --cron '0 1 * * *' \
  --tz America/Chicago \
  --command '/home/ubuntu/.openclaw/workspace/project-viewer/scripts/nightly-update.sh' \
  --command-cwd '/home/ubuntu/.openclaw/workspace/project-viewer' \
  --timeout-seconds 900 \
  --no-output-timeout-seconds 120 \
  --output-max-bytes 200000

Note: OpenClaw 2026.7.1-2 does not expose --failure-alert* flags on openclaw cron add. For this build, failure monitoring should come from openclaw cron runs, --webhook <url>, or a small wrapper script that sends an alert only when scripts/nightly-update.sh exits nonzero.

Then verify:

openclaw cron list
openclaw cron run <new-job-id> --wait --wait-timeout 1200000
openclaw cron runs --id <new-job-id> --limit 5

Operational effect:

Nightly docs keep publishing, but the dangerous part - open-ended agent review with tools - is removed from the nightly critical path.

4. Move Agent-Based Docs Review To Weekly Or Manual

Why:

The valuable part of the old job was not the nightly publish. It was the editorial judgment: harmonizing stale project claims, catching contradictions, and asking Andy canon questions. That does not need to run every night, and it should not be coupled to publish reliability.

Implementation option A - weekly cron:

openclaw cron add \
  --name docs-weekly-agent-review \
  --description "Weekly agent review of docs for stale claims, contradictions, and canon questions. Publish only after deterministic checks pass." \
  --cron '30 8 * * 6' \
  --tz America/Chicago \
  --agent main \
  --session isolated \
  --message "Run a bounded weekly Aspen Frost docs review. Read /home/ubuntu/.openclaw/workspace/project-viewer/prompts/nightly-doc-review.md, but treat it as weekly review guidance. Keep scope to project/status contradictions and obvious stale claims. Avoid broad repo spelunking unless directly needed. If edits are made, run cd /home/ubuntu/.openclaw/workspace/project-viewer && npm run build && node scripts/check-links.js && ./scripts/publish.sh. Final response: concise summary and any canon questions." \
  --thinking low \
  --timeout-seconds 900 \
  --tools exec,read,write \
  --channel telegram \
  --to 8779808012 \
  --account default \
  --announce

Implementation option B - manual only:

openclaw agent --message "Run a bounded Aspen Frost docs review using /home/ubuntu/.openclaw/workspace/project-viewer/prompts/nightly-doc-review.md, then publish if checks pass."

Operational effect:

Agent judgment remains available, but the expensive discretionary work is no longer part of a nightly reliability path.

5. Add A Systemd Memory Boundary For The Gateway

Why:

The OOM killer killed the gateway after the whole host was already badly degraded. A service-level memory limit should fail OpenClaw earlier and more cleanly, leaving enough headroom for SSH, journald, networkd, Docker, and recovery tooling.

Recommended starting point on the current 3.7 GiB host:

  • MemoryHigh=2800M
  • MemoryMax=3300M
  • Restart=always
  • RestartSec=10

How:

systemctl --user edit openclaw-gateway.service

Add:

[Service]
MemoryHigh=2800M
MemoryMax=3300M
Restart=always
RestartSec=10

Then:

systemctl --user daemon-reload
systemctl --user restart openclaw-gateway.service
systemctl --user status openclaw-gateway.service --no-pager

Operational effect:

The gateway may restart sooner under runaway memory, but the host is less likely to become unrecoverable. This is a containment measure, not a root-cause fix.

Risk:

If normal OpenClaw operation regularly exceeds these values, the gateway may restart too often. If that happens, either raise the host size or lower routine concurrency before raising the memory cap.

6. Add A Lightweight Host Watchdog

Why:

The host showed warning signs for more than an hour before the OOM kill. A watchdog can alert or restart the gateway while there is still enough headroom to recover.

Implementation path:

Create a small script that checks:

  • Available memory under 500 MB
  • Swap usage over 80%
  • Load average over 20 for 10+ minutes
  • Gateway RSS over 2.8 GB
  • Network reachability to Telegram or a neutral endpoint

Response ladder:

  • Log status.
  • If memory is bad but network works, send Telegram alert.
  • Restart openclaw-gateway.service.
  • If network is also unreachable and swap is saturated, leave a clear log and rely on host reboot/manual intervention.

Suggested first implementation:

mkdir -p /home/ubuntu/.openclaw/workspace/ops/scripts

Create /home/ubuntu/.openclaw/workspace/ops/scripts/openclaw-host-watchdog.sh with checks only first. Run it from user cron or OpenClaw command cron every 5 minutes after it is reviewed.

Operational effect:

Turns a silent multi-hour death spiral into an alertable, logged condition.

7. Consider Scaling The Lightsail Instance

Why:

The current instance has about 3.7 GiB RAM and 2 CPUs. That is tight for a multi-agent OpenClaw setup with Telegram providers, embedded Codex app servers, Docker sandboxes, hooks, cron jobs, docs builds, and occasional repo work.

Recommended threshold:

If the gateway still exceeds 2.5 GB RSS during normal usage after disabling/replacing the nightly agent cron, move to an 8 GB instance.

How:

  • Take a Lightsail snapshot.
  • Create a larger instance from the snapshot, preferably 8 GB RAM.
  • Preserve the static IP attachment.
  • Boot and verify:
free -h
systemctl --user status openclaw-gateway.service --no-pager
openclaw status
openclaw cron status
  • Send a Telegram test message through each active bot.

Operational effect:

Scaling buys headroom. It does not replace cron hardening, but it makes OpenClaw less brittle when multiple agents or tool sessions overlap.

Recommended Execution Order

  • Disable docs-nightly-review-publish.
  • Run ./scripts/nightly-update.sh manually once and verify docs publish still works.
  • Add the deterministic command cron for nightly publish.
  • Add service-level memory boundaries.
  • Watch the host for 48 hours.
  • Reintroduce agent docs review weekly or manual.
  • Decide whether to resize Lightsail based on measured gateway RSS and swap behavior.

Open Questions

  • Should nightly docs publishing prioritize deterministic freshness over editorial review? My recommendation: yes.
  • Should agent-based docs review move to weekly? My recommendation: yes, unless Andy actively wants nightly editorial maintenance.
  • Is the current 4 GB Lightsail instance still the right size for the agent team? My recommendation: probably not long term; keep it only if hardening stabilizes memory.
  • Should OpenClaw itself enforce child-process cleanup after cron timeout? My recommendation: yes. This incident looks like a platform-level reliability gap worth upstreaming or fixing locally if we own that layer.

Bottom Line

The failure mode was not mysterious: broad nightly agent cron, sustained swap exhaustion, runaway load, OOM kill, then damaged network state. The fix is to remove discretionary agent work from nightly critical paths, put hard memory boundaries around the gateway, and scale the box if observed memory remains high.
