Engineering PR-to-Release Loop Review

Aspen | 2026-09-07 | Revision: v1.1 | Status: Draft for Andy review | Evidence: Frost Rocks PRs #27-#37 and Andy's process corrections

Verdict

The technical work was generally more disciplined than the visible process. Arya, Jesse, and Cassian did substantive scoping, implementation, review, testing, build, and device-gate work. The loop is loose because those actions are recorded across Telegram conversations, local agent memory, project Markdown, GitHub, EAS, and Andy's instructions rather than in one deterministic state transition.

What the last eleven PRs show

  • GitHub reports zero formal reviews on PRs #27-#37, although Cassian's dated memory records reviews, requested changes, exact-head verification, approvals, merges, builds, and submissions for many of them.
  • GitHub attributes the merges to Andy's frostymug account, but Cassian's memory records that Cassian performed many of those actions using Andy's GitHub credentials. This is an identity/audit defect, not evidence that Andy manually operated every merge.
  • PR bodies repeatedly use phrases such as “physical gate before merge,” “device gate,” and “release gate” for different moments. In practice, some changes had to merge and reach TestFlight before physical proof was possible. The intended boundaries were often sound, but the vocabulary was not.
  • Cassian frequently combined four roles in one pass: independent reviewer, merge operator, build operator, and release recorder. That is efficient, but it makes the handoff hard to audit and allows the reviewer to silently become the integrator.
  • Arya authored PR #29 directly even though the standing model says Jesse implements and Arya reviews. That may have been justified by urgency or complexity, but the role exception was not explicitly recorded.
  • Builds #26-#34 followed in rapid succession, sometimes one build per merged PR. This produced strong exact-commit provenance, but also created multiple overlapping TestFlight states and device matrices.
  • Shared project status drifted behind reality: WORK.md still described PR #27 as open after PR #37 had merged, and README.md contained both current and stale PR #27 state.
  • Cassian has no isolated GitHub CLI configuration and therefore falls back to shared/global credentials. Arya and Jesse already have isolated GitHub identities; Cassian needs the same treatment.
  • The private repository cannot use GitHub branch protection or rulesets on the current plan, so determinism must initially come from workflow automation and a required written protocol rather than protected-branch enforcement.

Revised small state machine

For the current one-user/TestFlight phase, use four states:

  • SCOPED — Arya turns Andy's requirements into a numbered work package with scope, acceptance checks, exclusions, sequencing, and whether it needs a TestFlight build. Andy approves the package before implementation.
  • PR READY — Jesse opens the PR against that work package; CI passes; Arya records exact-head scope/architecture approval; Cassian records exact-head reliability approval. Requested changes keep it in this state.
  • TESTFLIGHT CANDIDATE — Cassian merges and starts one EAS build configured to submit automatically when the build succeeds. The record includes PR, source commit, build number/ID, and App Store Connect submission status. If several safe PRs can share one build, Cassian batches them.
  • DEVICE VALIDATED — Andy installs the named TestFlight build and runs its focused checks. Pass closes the work package; failure returns a bounded defect to SCOPED.

TestFlight is the current physical-device validation environment. It is not evidence that device validation already passed, and it is not a public production release. There is no separate pre-TestFlight physical gate today because TestFlight is how the app reaches the only physical tester. A distinct exposure/public-release gate should be added later when the tester cohort expands beyond Andy or the app approaches public release.

Top of funnel: work package before PR

The missing record currently exists between Andy's requirements and Jesse's PR. Fix it with a lightweight work package before coding begins.

  • Store it in projects/<project>/WORK.md plus a focused scope document when needed.
  • Give it a stable ID, owner, intended PR title, acceptance checks, exclusions, dependencies, and TestFlight requirement.
  • Arya owns the technical scope; Aspen verifies the handoff exists; Andy approves it in chat or the published artifact.
  • Jesse names the work-package ID in the branch, PR title/body, and closing comment.

A GitHub issue can mirror the package for execution convenience, but the shared project folder remains the cross-agent source of truth. For small fixes, the WORK.md row plus a short GitHub issue is enough; do not manufacture a miniature architecture document.

Build and submission automation

Cassian must not promise to return after an asynchronous EAS build completes. An isolated agent turn does not reliably resume itself.

For Frost Rocks, start the build and submission as one EAS operation:

eas build --platform ios --profile testflight --auto-submit-with-profile production --non-interactive

EAS then queues App Store Connect submission automatically after a successful build. Cassian records the EAS build ID immediately and may later check status, but no second human prompt is required to trigger submission. A failed build or failed submission becomes a visible failed candidate, not an unfinished promise.

Identity correction

Cassian needs an isolated GitHub identity comparable to aspenfrost-arya and aspenfrost-jesse. Until that exists, GitHub's actor field cannot distinguish Andy from Cassian and should not be used to infer who operated a merge.

Required setup:

  • Create a dedicated Cassian GitHub account or GitHub App identity with access limited to Aspen Frost repositories.
  • Store its CLI authentication under /home/ubuntu/.openclaw/agents/cassian/gh.
  • Set Cassian's GH_CONFIG_DIR to that directory in OpenClaw configuration.
  • Require Cassian to post reviews, merges, and release-ledger updates only through that identity.
  • Verify with gh api user before the next pilot PR.

Required system of record

GitHub should carry the PR review state even if enforcement is unavailable:

  • Arya and Cassian post reviews or structured PR comments from their own GitHub identities, including exact head SHA and one of the named gate states.
  • A single PR comment is updated as the delivery ledger for scope/PR approval, TestFlight candidate, and device-validation states.
  • Local agent memory may preserve detail, but it is never the only evidence that a gate passed.
  • Project docs point to the ledger; they do not duplicate fast-changing operational state unless it affects the durable project story.

Role boundaries

  • Jesse: implementation owner; may not self-approve architecture or reliability.
  • Arya: architecture/code reviewer; may implement only when the handoff explicitly records a role exception and names an independent code reviewer.
  • Cassian: reliability and TestFlight operator; after both review checks pass, merges and starts the auto-submitting TestFlight candidate as one operation when the work package calls for a build.
  • Aspen: state-machine owner; detects missing gates, stale records, or ambiguous ownership and stops the handoff before it becomes archaeology.
  • Andy: approves product/phase exceptions and supplies physical-device evidence when he is the tester; he should not need to manually narrate ordinary micro-handoffs.

Recommended pilot

Use the next Frost Rocks PR as the pilot. Do not retrofit eleven historical PRs. Create its work package before Jesse starts, create the delivery-ledger comment at PR open, require Arya and Cassian to record their exact-head decisions on GitHub, use automatic submission when a TestFlight build is warranted, and evaluate whether Andy can understand the entire state without reading agent memory.
