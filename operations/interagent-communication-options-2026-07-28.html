Interagent Communication Options

Decision brief for Andy Frost Date: 2026-07-28 Status: Research complete; recommendation proposed; no configuration changes made

Executive Summary

Andy currently has to manually trigger each handoff between specialist agents. This is especially cumbersome in two recurring loops:

  • Product loop: Izzy → Petra → Arya
  • Engineering loop: Arya → Jesse → Cassian

The recommended solution is Aspen-led workflow orchestration, supported by narrowly controlled agent-to-agent messaging.

Andy would assign the outcome once to Aspen. Aspen would manage sequencing, verify each shared artifact, enforce approval gates, trigger the next specialist, and return a consolidated result.

A shared Telegram group should not be used as the underlying communication bus. Telegram prevents bots from receiving messages sent by other bots, so the room would look shared to Andy while the agents actually retained separate and incomplete views.

Desired Outcome

Reduce this:

  • Ask Arya to produce an architecture.
  • Wait for completion.
  • Open Jesse's chat.
  • Explain where Arya left the artifact.
  • Ask Jesse to implement it.
  • Wait for completion.
  • Open Cassian's chat.
  • Explain what Jesse finished.
  • Ask Cassian to deploy it.

To this:

> Aspen, run the approved engineering loop for Project X through TestFlight.

Aspen would then coordinate Arya → Jesse → Cassian while preserving Andy's required approval gates.

Option 1: Shared Telegram Team Channels

Possible rooms:

  • Product Room: Izzy, Petra, Arya, Aspen
  • Engineering Room: Arya, Jesse, Cassian, Aspen

Andy could mention the agent responsible for each task while all bots receive his messages.

Advantages

  • One visible place for Andy to operate each loop.
  • All agents can receive Andy's framing, corrections, and approvals.
  • Fewer separate direct-message conversations.
  • A human-readable record organized by team or project.

Limitations

  • Telegram bots cannot receive messages sent by other bots, regardless of privacy mode or administrator status.
  • Arya's visible response would therefore not automatically reach Jesse or Cassian.
  • Each OpenClaw agent would still maintain an isolated group session rather than sharing one transcript.
  • Disabling Telegram privacy mode would make every bot ingest more human messages, increasing token usage and accidental activation risk.
  • OpenClaw's true multi-agent broadcast-group feature is currently experimental and WhatsApp-only.

Verdict

Useful as a human-facing command room or dashboard, but not dependable as the interagent handoff mechanism.

Option 2: Direct Agent-to-Agent Messaging

OpenClaw supports cross-agent communication through sessions_send. It is disabled by default and must be explicitly enabled with an agent allowlist and appropriate session visibility.

A handoff could look like:

> Architecture approved for implementation. Canonical artifact: projects/example/ARCHITECTURE.md. Build only the approved scope and report blockers to Aspen.

OpenClaw marks these messages as inter-session data rather than direct human-authored instructions. It can also permit a bounded reply-back exchange between agents.

Advantages

  • Eliminates Andy's manual handoff message.
  • Preserves separate agent identities, workspaces, credentials, and tool permissions.
  • Fits the existing shared-artifact system: the file remains canonical and the message triggers action.
  • Can be restricted to explicitly allowlisted agents.
  • Provides a foundation for later workflow automation.

Risks

  • Increases agent autonomy across a boundary previously reserved for Trust Ramp Phase 2.
  • Broad session visibility could expose more cross-agent context than necessary.
  • Unbounded exchanges can create loops, unclear ownership, duplicated work, and token waste.
  • An agent might trigger downstream work before an Andy approval gate.
  • Transient messages could be mistaken for canonical project state.

Verdict

Technically appropriate when constrained. It should be treated as a formal handoff channel, not unrestricted agent conversation.

Option 3: Aspen as Workflow Orchestrator

Andy assigns a multi-stage outcome once. Aspen owns the workflow state and coordinates each specialist.

For the product-feasibility loop, Aspen would:

  • Ask Izzy for the design artifact.
  • Verify that it was promoted to the shared project folder.
  • Ask Petra for the specified strategic or customer review.
  • Route the resulting package to Arya for feasibility.
  • Return a consolidated decision packet to Andy.

For the engineering loop, Aspen would:

  • Confirm the architecture and Andy approval gate.
  • Trigger Jesse with the exact approved scope and acceptance criteria.
  • Verify implementation and test evidence.
  • Trigger Cassian for release verification and deployment.
  • Report the outcome, failures, or required decision to Andy.

Advantages

  • Andy assigns the outcome once.
  • One owner tracks what is waiting, completed, rejected, or blocked.
  • Approval and safety gates are enforced centrally.
  • Each specialist receives a narrowly framed request with exact artifacts and completion criteria.
  • Handoffs are easier to audit.
  • The model directly matches Aspen's Integrator role.

Tradeoffs

  • Aspen becomes a coordination dependency.
  • Each workflow needs explicit stage and completion definitions.
  • OpenClaw still needs a controlled mechanism for Aspen to invoke the other agents.
  • Premature overengineering could create unnecessary workflow bureaucracy.

Verdict

Best fit for the current organization and Trust Ramp.

Recommendation

Adopt Option 3 as the operating model, powered by a constrained implementation of Option 2.

Operating Rules

- canonical artifact path; - artifact status and provenance; - requested action; - completion criteria; - required next recipient; - whether Andy approval is required before proceeding.

  • Andy initiates or advances a multi-agent workflow through Aspen.
  • Aspen owns sequencing, status, handoff quality, and approval gates.
  • Canonical deliverables remain under projects/<project>/.
  • Messages trigger work but never replace shared artifacts or project status.
  • Each handoff states:
  • Initial agent messaging should route completion back to Aspen.
  • Specialist agents should not autonomously cross an Andy approval gate.
  • Agent reply-back exchanges should be limited to one or two turns.
  • Existing Telegram direct messages remain available for Andy to interrogate or redirect individual specialists.

Proposed Rollout

Stage 1: Aspen-Coordinated Pilot

Pilot the Arya → Jesse → Cassian engineering workflow.

  • Andy starts the workflow once through Aspen.
  • Aspen performs and records each handoff.
  • Every gate remains visible to Andy.
  • No agent independently initiates the next approval-sensitive stage.

Stage 2: Measured Delegation

After the pilot demonstrates reliable artifacts, completion contracts, and stopping behavior:

  • Permit selected specialists to initiate explicitly approved downstream handoffs.
  • Keep Aspen informed as workflow owner.
  • Expand only where the reduced friction outweighs the added autonomy and context exposure.

Current Configuration

As of 2026-07-28:

  • Telegram group handling is disabled.
  • Agent-to-agent messaging is unset, which means effectively disabled.
  • No configuration was changed as part of this research.
